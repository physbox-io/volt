# Circuit Expert Developer & Environment Guide

This document captures environment configurations, path resolutions, and workflow tips for developing Circuit Expert inside Windows Subsystem for Linux (WSL).

## 💻 WSL Development & Node Execution Workflow

### 1. 🖧 Windows/WSL Path Mappings & Command Execution
* **Path Resolution**: The workspace files are accessed in Windows via UNC paths (`\\wsl.localhost\Ubuntu-20.04\home\boab\circuit`). However, Windows-based `npm`/`npx` tools will fail with UNC path errors or `ERR_INVALID_URL` because standard Windows Node/npm cannot resolve UNC paths natively in CMD.
* **Avoid Host Leakage**: Calling `npm` directly on the Windows host inside a WSL workspace directory can default to running Windows `npm.cmd` via `cmd.exe`, resulting in errors like `'tsc' is not recognized as an internal or external command`.
* **WSL NVM Environment Execution**: Node/npm are managed via NVM inside WSL (e.g. `~/.nvm/`). Because NVM is initialized in `.bashrc` / `.bash_profile`, non-interactive shells cannot resolve node or npm commands. If standard commands fail, explicitly export the NVM Node path to your `PATH` or use an interactive/login bash shell:
  ```bash
  # Execute dev server using NVM path:
  wsl -d Ubuntu-20.04 -e bash -c "export PATH=/home/boab/.nvm/versions/node/v20.20.0/bin:/usr/local/bin:/usr/bin:/bin; cd /home/boab/circuit && npm run dev"

  # Run build using NVM path:
  wsl -d Ubuntu-20.04 -e bash -c "export PATH=/home/boab/.nvm/versions/node/v20.20.0/bin:/usr/local/bin:/usr/bin:/bin; cd /home/boab/circuit && npm run build"
  ```

## 🔌 CYD/Heltec HIL Debugging (`~/cyd-native`, Ubuntu-24.04 WSL distro)

* **Cross-distro access**: `~/cyd-native` lives in the `Ubuntu` (24.04) WSL distro, not this one (`Ubuntu-20.04`). Reach it from here via `wsl.exe -d Ubuntu -e bash -c "..."`. Expect a harmless `chdir(...)` error line on every invocation (interop quirk from the two distros' differing CWDs) — ignore it and read the real output below it. Prefer `/bin/cat`/explicit binary paths over bare `cat` if the target shell has custom aliases.
* **`print()` vs `sys.stdout.write()` in `lib/heltec.py` / `lib/webserver.py`**: only `print()` reaches the browser's REPL console. `builtins.print` is monkeypatched (`lib/webserver.py`, `builtins.print = web_repl_print`) to broadcast over the WebSocket; `sys.stdout.write()` bypasses that entirely and goes only to the CYD's physical serial console (invisible unless you have a serial monitor attached). When adding debug prints anywhere in these files, always use `print()`, never `sys.stdout.write()`.
* **`print()` only broadcasts *during* an active `execute_repl()` call**: `web_repl_print` checks `repl_buffer is not None` before broadcasting, and `execute_repl()` resets `repl_buffer = None` in its `finally` block right before returning. So `print()` calls in code that runs *after* `execute_repl()` returns (e.g. in `handle_request`'s dispatch loop, timing a whole `repl_input` round trip) will silently fall back to real-serial-only output too. For debug output outside the exec window, call `broadcast_ws(json.dumps({"type": "repl_output", "output": "...", "code": ""}))` directly instead — same mechanism `web_repl_print` uses internally, but without the `repl_buffer` gate.
* Net lesson: if a debug print you just added "isn't showing up" in the browser console, check both of the above before assuming the code path isn't executing at all.

## ⚡ HIL Pipeline Architecture & Performance (browser ↔ CYD ↔ Heltec)

Data flow: browser runs the actual SPICE simulation (ngspice-wasm in a Web Worker) → sends compact commands over WebSocket to the CYD (MicroPython) → CYD relays over UART to the Heltec (C++/Arduino, owns the real GPIO pins) → Heltec replies once per command.

* **Lookahead queue, not single-slot lookahead** (`App.tsx`: `hilQueueRef`, `topUpHILQueue`, `runHILSimulationSlice`): SPICE compute time per slice is inherently lumpy — a slice landing on a switching edge costs much more than one that doesn't (adaptive timestep needs finer resolution near a transistor's turn-on transition). A single-slot "compute exactly the next slice" lookahead has zero margin for that lumpiness: one slow compute call starves the device mid-blink (visible freeze). Fix was a real queue: compute in fixed `HIL_SLICE_STEP_MS` (40ms) steps, keep `HIL_BUFFER_TARGET_MS` (240ms) worth buffered ahead at all times.
* **Two granularities, don't conflate them**: `HIL_SLICE_STEP_MS` (40ms) is the SPICE *compute* granularity (fine, for queue smoothing). `HIL_BATCH_TARGET_MS` (120ms, `mergeAndDequeueHILBatch`) is the *dispatch* granularity — several computed slices get merged into one outgoing command to cut round-trip count. These serve different purposes; don't "simplify" by making them the same value.
* **Two CYD-side execution modes, kept side by side on purpose** (`cyd-native/lib/webserver.py`):
  - `hil_slice` / `handle_hil_slice` (legacy): CYD's MicroPython loops `gpio_write()`/`adc_read()` itself — each one is its own **blocking UART round trip to the Heltec** (~11ms measured on this link). Simple, always works, but a burst with several toggle edges pays ~11ms of both latency *and* real timing distortion **per edge** (each edge's actual hold duration balloons by ~11ms beyond intended).
  - `hil_batch` / `handle_hil_batch` (native): CYD forwards the whole `writes`/`reads` payload in **one** UART transaction; the Heltec's own C++ firmware (`heltec/src/uart_cmd.cpp`, `handle_hil_batch`) runs the write/sleep/read loop natively and replies once. Requires Heltec firmware built with this handler — a real PlatformIO rebuild + reflash, not just a MicroPython/JS redeploy.
  - Selectable per-Heltec-node (`selectedNode.data.hilExecutionMode`, PropertiesPanel on the node itself — not a global setting, since it depends on what firmware that specific board is running). Defaults to `'native'`.
  - **Gotcha already fixed once, don't reintroduce it**: the write/sleep order inside the toggle-sequence loop matters. The sequence encoding is "hold this value for this long" (run-length pairs), so playback must be **write-then-sleep** (`digitalWrite(val); delayMicroseconds(delay)`), not sleep-then-write — the latter holds each value for the *next* entry's duration instead of its own, silently distorting waveform timing (this specifically broke when batching made bursts contain many edges instead of 0-1).
* **UART baud rate between CYD and Heltec is 460800** (bumped from 115200 once `hil_batch` started sending fewer-but-bigger consolidated messages, making transmission time — not just fixed per-message turnaround — start to matter). Two places must stay in sync if this ever changes again: `CydSerial.begin(...)` in `heltec/src/main.cpp`, and `Heltec.__init__`'s `baudrate` default in `cyd-native/lib/heltec.py` (every call site constructs `Heltec()` with no explicit baudrate, relying on that default via the singleton).
* **Adaptive HIL transient resolution** (`App.tsx`: `hilHalfPeriodMsRef`, `hilMaxStepMs`, `spice.ts`: `hilMaxStepMs` param on `generateSpiceNetlist`): the `.tran` step size for HIL slices scales to whichever tracked `digital_out` pin has the shortest recently-observed half-period, instead of a fixed 1ms — a fixed step is fine at a few Hz but badly under-resolves edges once a half-period drops to a few ms. Floored via `MAX_POINTS_PER_SLICE` (a named point-count budget, currently an **unvalidated placeholder**, not a measured limit) rather than a bare guessed number. The threshold-crossing glitch filter (`MIN_PULSE_US`) scales with whatever step size was actually used that slice (1.5×), not a flat constant, so it can never eat a real transition the sim is actually capable of resolving.
* **Known/estimated ceiling, not measured**: with current constants, the resolution-budget floor starts binding around a full period of ~0.4ms (~2.5kHz) — below that (including the "a few hundred Hz" range this was tuned for) resolution shouldn't be the limiting factor. The actual gating constraint — whether per-slice SPICE compute time reliably finishes inside the 40ms real-time budget — has **not** been measured/instrumented. Don't state a max frequency as fact without adding that profiling first.
* **Threshold-crossing digital-out derivation is generic, not tied to one pin**: any `digital_out` pin on a Heltec node gets its hardware sequence derived the same way (threshold-crossing against the actual simulated net voltage) — there used to be a bug where only `GPIO_3` got real behavior and every other `digital_out` pin was a hardcoded no-op; fixed, don't reintroduce a single-pin special case here.
* **Circuit is locked while any simulation is running** (`isSimulating` gates `onNodesChange`/`onEdgesChange`/`onConnect`/`onDrop`/`deleteSelected`, plus `nodesConnectable={!isSimulating}` on `<ReactFlow>`): needed because several HIL optimizations (e.g. `hilConnectedPinsCacheRef`) assume topology doesn't change mid-run. Value edits (resistor values, LDR light level, switch toggling) are still allowed live — those aren't topology changes and are an intentional live-tweak feature, don't gate those too.
* **ESP32-S3 (the Heltec board here) has no built-in analog DAC** — that peripheral was dropped vs. the original ESP32/ESP32-S2 (which have 2× 8-bit DAC channels). Relevant if real analog waveform output (not just GPIO square-wave toggling) ever comes up again: options are an external DAC chip, or a PWM (LEDC hardware peripheral) + RC-filter approximation. LEDC itself *is* the right tool for driving a GPIO pin at a precise frequency generically (hardware-timed, no software bit-banging loop) if "drive GPIO at voice-band frequencies" comes back as a goal — much better than trying to scale up the edge-list-over-UART approach used for slow (≤ a few hundred Hz) signals.
* See also project memory `project_spice_transistor_convergence` (NPN/PNP model must keep nonzero CJC/CJE/TR/TF or oscillator circuits become numerically unstable in ngspice-wasm) — same root circuit class (astable multivibrator) as the HIL work above.
